# Design: add-agent-core

## Context
LabSteward 的使用者是實驗室成員、財產管理人與 PI；輸出包含具行政效力的文件（採購清單、報廢申請）。系統必須可稽核，且法規門檻因校而異。

## Goals / Non-Goals
- Goals：LLM 只負責理解、追問、拆解與解釋；所有數值與合規判定由確定性元件產生；所有狀態變更可追溯。
- Non-Goals：不自動下單、不自動送出報廢；不取代學校正式財產系統，而是作為其前端與決策輔助。

## Decisions
1. **LLM 作為協調者而非求解器**：依 [4] 的結果，瓶頸在計算推理而非資訊不足，因此門檻、年限與折舊一律交給程式與規則引擎。
2. **規則寫成 YAML 而非 prompt**：法規修訂時只改設定檔並重跑測試，不需重寫 prompt；也讓「規則版本」可寫入稽核紀錄。
3. **狀態機控制流程（LangGraph 或自寫）**：可明確設定追問上限、重搜上限與人工核准節點，避免 Agent 無限迴圈。
4. **混合檢索（BM25 + 向量 + 數值過濾）**：法規條文含大量數字與專有名詞，單純向量檢索命中率不足 [9]。

## Three Design Trade-offs
| Trade-off | 選擇 | 代價 | 緩解 |
|---|---|---|---|
| 自主程度 ↔ 人工核准 | 會改變狀態的動作一律人工核准 | 流程較慢 | 低風險唯讀查詢不需核准；核准畫面附證據與違規清單 |
| LLM 彈性 ↔ 規則確定性 | 規則引擎判定、LLM 解釋 | 規則需人工維護，未涵蓋情境無法判定 | 未涵蓋時回傳 UNKNOWN_RULE 並轉人工 |
| 追問完整性 ↔ 使用者負擔 | 追問上限 T_max（預設 3） | 資訊可能仍不足 | 超過上限時輸出部分結果並標示 NEED_INFO |

## Risks / Mitigations
- Prompt injection（使用者或網頁內容要求繞過核准）→ 核准節點在程式層強制，不受 LLM 輸出影響。
- 法規 RAG 引用錯條文 → 規則引擎結果優先於 RAG 文字；評估時量測引用正確率。

## Open Questions
- Agent 建議錯誤時的責任歸屬，以及 LLM 推理過程需保留到什麼程度才符合稽核要求。
